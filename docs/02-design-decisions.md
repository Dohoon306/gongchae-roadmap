# 02. 1차 범위 설계 결정

`/grill-with-docs`로 1차 범위(입력 → AI 분석 → 공고 추천 → 공고 선택 → 통합 로드맵, 로그인 없음, 기능이 끝난 뒤 인프라)를 설계하며 정한 것을 적는다. 용어는 `GLOSSARY.md`, 백엔드 구조는 `docs/architecture.md`를 따른다.

## 정한 것

| # | 질문 | 결정 | 날짜 |
|---|---|---|---|
| Q1 | 흐름의 중심 객체 | AI 분석 결과를 `지원자 프로필`로 DB에 저장하고 ID를 준다. 추천과 로드맵은 프로필 ID를 참조한다. 1차에는 인가가 없어 ID를 아는 누구나 볼 수 있다. 2차에 프로필에 회원 참조가 붙는다. | 2026-11-26 |
| Q2 | 사용자가 고르는 단위 | 기관이 아니라 공고를 고른다. ~~로드맵은 고른 공고마다 하나씩 만든다~~(Q8에서 통합 로드맵으로 바뀜). 화면에서 기관별로 묶어 보여 준다. 마감된 공고를 고르면 "비슷한 공고가 다시 나올 때를 대비하는 로드맵"이 된다. `01-idea.md`의 "기관 선택"을 "공고 선택"으로 고쳤다. | 2026-11-26 |
| Q3 | 추천의 위치와 저장 | 별도 `recommendation` 도메인에 둔다. 추천은 프로필 ID와 공고 ID를 참조하고 순위와 이유를 가진다. 만든 시점의 스냅숏으로 저장하며 다시 열어도 같다. 1차에서는 지원자 프로필 하나에 추천을 한 번만 만든다. 새 추천이 필요하면 흐름을 처음부터 다시 한다(새 프로필). 같은 프로필에서 "다시 추천받기"는 2차에서 정한다. | 2026-11-26 |
| Q4 | 마감된 공고의 추천 | 마감 공고도 추천한다. 추천 목록을 `진행 중 공고`와 `마감 공고`(다음 채용 대비 참고용) 구역으로 나누고 진행 중 공고를 먼저 보여 준다. 구분 기준은 접수 마감일이 오늘보다 앞인지다. 같은 채용의 다음 회차가 있으면 옛 공고를 빼는 규칙은 실제 잡알리오 데이터를 본 뒤 2차에서 검토한다. | 2026-11-26 |
| Q5 | 공고의 저장과 수집 | `posting` 도메인에 `공고` Entity를 두고 우리 DB에 저장한다. 추천은 DB에 있는 공고만 대상으로 한다. 외부 출처의 인터페이스는 `posting/domain`, 구현체(샘플 데이터, 잡알리오)는 `posting/infra`에 둔다. 외부 일련번호를 공고의 필드로 보관해 중복 저장을 막는다. 1차의 수집은 애플리케이션 시작 시 한 번 실행하고 이미 있는 공고는 건너뛴다. 주기적 자동 수집은 실제 API를 붙인 뒤에 정한다. | 2026-11-26 |
| Q6 | 입력 방식과 프로필 | `profile` 도메인. 두 입력 방식 모두 같은 `지원자 프로필`을 만든다. 직무 분류만 고르면 AI를 부르지 않고 관심 직무 분류만 채운 프로필을 만든다. 이력서·자기소개서를 올리면 AI가 전공, 기술, 경험, 관심 직무 분류를 뽑는다. 둘을 함께 주면 관심 직무 분류는 사용자가 고른 값을 쓰고 나머지는 AI가 채운다. AI 호출 인터페이스는 `profile/domain`, 구현체는 `profile/infra`에 둔다. | 2026-11-26 |
| Q7 | 추천 계산 방식 | 두 단계로 계산한다. (1) 프로필의 관심 직무 분류와 같은 직무 분류를 가진 공고를 DB에서 찾아 진행 중 공고와 마감 공고를 각각 최대 N건으로 자른다(N은 10으로 시작해 샘플 데이터로 조정). (2) 후보와 프로필을 AI에 보내 순위와 이유를 받아 `추천`으로 저장한다. 직무 분류만 있는 프로필은 (2)를 건너뛰고 접수 마감일이 가까운 순으로 순위를 매기며 이유는 고정 문장으로 채운다. 순위·이유용 AI 호출 인터페이스는 `recommendation/domain`, 구현체는 `recommendation/infra`에 둔다. 학력 조건, 근무 지역 등 추가 조건으로 거르는 것은 1차에 넣지 않는다. | 2026-11-26 |
| Q8 | 공고 선택과 로드맵의 형태 | `roadmap` 도메인. 지원자 프로필 하나에 통합 `로드맵` 하나를 둔다. 로드맵은 프로필 ID, 고른 공고 ID 목록, 단계 목록을 가지며 단계마다 어느 공고에 해당하는지 표시한다. 고른 공고 목록이 선택의 기록이고 선택을 따로 저장하지 않는다. 공고를 바꿔 다시 만들면 기존 로드맵을 교체한다. `roadmap`은 `recommendation`을 참조하지 않으며 "추천받은 공고만 고를 수 있다"는 검사는 하지 않는다. **일정 조정을 1차에 넣는다**(`01-idea.md`의 1차 범위를 넓힘. 달력·간트 차트 시각화는 그대로 2차). | 2026-11-26 |
| Q9 | 전형 단계와 준비 단계 | `공고`는 `전형 단계` 목록을 가진다. 전형 단계는 `전형 종류`(서류, 필기, 면접, 기타)와 날짜를 가지며 날짜는 없을 수 있다. 잡알리오의 자유 텍스트를 이 목록으로 바꾸는 일은 잡알리오 구현체(`posting/infra`) 안에서 한다(AI 사용 예상, 실제 API를 붙일 때 만들고 정확도를 검증한다). 샘플 데이터 구현체는 처음부터 구조화된 전형 단계를 준다. 로드맵의 `준비 단계`는 고른 공고들의 전형 단계를 전형 종류별로 합쳐 만들고(종류마다 하나, 해당 공고 표시), 준비 내용은 AI가 지원자 프로필과 해당 공고를 보고 쓴다. 준비 내용용 AI 호출 인터페이스는 `roadmap/domain`에 둔다. | 2026-11-26 |
| Q10 | 일정 조정 | AI가 아니라 규칙으로 계산한다. (1) 기한: 준비 단계에 해당하는 공고마다 기한을 붙인다. 서류 준비는 접수 마감일, 필기·면접 준비는 그 전형 단계의 날짜다. (2) 순서: 준비 단계를 가장 이른 기한 순으로 늘어놓는다. (3) 겹침: 서로 다른 공고의 전형 날짜가 같은 날이면 표시한다. (4) 날짜가 없으면 "날짜 미정"으로 두고 뒤쪽에 놓는다. 마감 공고의 지난 날짜는 일정에 쓰지 않는다. **비어 있는 날짜는 사용자가 직접 입력해 채운다.** 계산은 `로드맵` Entity의 메서드로 쓰고 테스트로 검증한다. AI가 주 단위 계획을 짜는 것과 사용자 여건(공부 시간)에 따른 배분은 2차에서 검토한다. | 2026-11-26 |
| Q11 | 할 일 계획과 날짜 입력 | 준비 단계 안에 `할 일` 목록을 둔다. AI는 지원자 프로필과 해당 공고들을 보고 준비 단계마다 할 일과 각 할 일의 비중을 쓴다. 날짜는 AI가 정하지 않는다. 할 일의 기간은 규칙으로 계산한다: 로드맵을 만든 날부터 그 준비 단계의 가장 이른 기한까지를 비중대로 나눈다. 기한이 "날짜 미정"이면 할 일을 날짜 없이 순서대로만 보여 준다. 사용자가 입력한 날짜는 `공고`가 아니라 `로드맵`에 저장하고, 공고의 날짜보다 우선한다(마감 공고에도 입력 가능). 입력은 로드맵을 만든 뒤 로드맵 화면에서 하며, 입력하면 할 일의 기간, 순서, 겹침 표시를 다시 계산하고 AI는 다시 부르지 않는다. 준비 단계끼리 기간이 겹치는 것은 허용한다. 하루 공부 시간에 맞춘 배분과 날짜 외 정보 입력은 2차로 둔다. | 2026-11-26 |
| Q12 | 도메인끼리 데이터를 읽는 방법 | 다른 도메인의 데이터는 그 도메인의 Service를 호출해 읽기 전용 객체로 받는다. Entity에는 상대의 ID 값만 두고 도메인을 넘는 JPA 연관 관계를 맺지 않으며, 다른 도메인의 Repository를 직접 쓰지 않는다. 호출 방향은 `recommendation`, `roadmap` → `profile`, `posting` 한쪽이다. ADR 0004. | 2026-11-26 |
| Q13 | AI 연동 구성 | AI 호출 인터페이스는 셋이다: `profile`(이력서 글 → 프로필 내용), `recommendation`(프로필 + 후보 공고 → 순위와 이유), `roadmap`(프로필 + 고른 공고 → 준비 단계별 할 일과 비중). 인터페이스마다 OpenAI 구현체와 가짜 구현체(정해진 답)를 각 도메인의 `infra`에 두고 설정으로 고른다. 기본은 가짜 구현체이고, OpenAI 키를 환경 변수로 넣었을 때만 실제 구현체가 켜진다. OpenAI와 통신하는 공통 코드는 `global`에 한 번만 두며 Spring AI 라이브러리를 쓴다(버전과 사용법은 명세 단계에서 공식 문서로 확인). 각 도메인의 OpenAI 구현체는 질문 만들기와 답을 도메인 객체로 바꾸기만 맡는다. | 2026-11-26 |
| Q14 | 이력서 PDF 처리와 개인정보 | PDF는 디스크에 저장하지 않는다. 메모리에서 글을 뽑아 AI에 보낸 뒤 버리며, 파일도 뽑은 글도 DB와 디스크에 남기지 않는다. PDF에서 글을 뽑는 일은 `profile/infra`에 둔다. 글이 없는 PDF(스캔 이미지)는 "글을 붙여넣어 주세요"라는 안내를 돌려준다. 파일 크기 상한은 5MB다. **이름과 연락처는 AI에 보내기 전에 가린다(마스킹). 1차에 넣는다.** 입력 화면에 "실제 AI 분석을 켜면 입력한 내용이 OpenAI로 전송됩니다"라는 안내를 넣는다. 개발과 테스트에는 지어낸 이력서만 쓴다. | 2026-11-26 |
| Q15 | 이름과 연락처를 가리는 방법 | 연락처(전화번호, 이메일)와 주민등록번호 형식은 형식 규칙으로 찾아 가린다. 이름은 두 방법을 함께 쓴다: (1) "이름:", "성명:" 같은 라벨 뒤의 값을 이름으로 보고 글 전체에서 같은 글자를 가린다. (2) 입력 화면에 선택 항목 "가릴 이름" 칸을 두고, 채워지면 그 이름도 가린다. 받은 이름은 저장하지 않는다. 가린 자리는 `[이름]`, `[전화번호]`, `[이메일]`처럼 표시한다. 가리는 규칙은 `profile/domain`에 두고 붙여넣은 글과 PDF에서 뽑은 글 모두에 적용하며, 가짜 구현체를 쓸 때도 똑같이 적용해 테스트로 검증한다. 주소는 1차에서 가리지 않는다. | 2026-11-26 |
| Q16 | DB 종류 | 실행은 Docker Compose로 띄운 MySQL, 테스트는 메모리 H2(MySQL 호환 모드)를 쓴다. 테스트가 창마다 자기 메모리 DB를 써서 여러 herdr 창이 동시에 돌려도 부딪히지 않는다. 두 DB의 문법 차이는 Repository만 쓰는 규칙으로 줄인다. 접속 정보는 환경 변수로 읽는다. 확인한 환경: Java 17, Docker, Node 24 설치됨. | 2026-11-26 |
| Q17 | ID 형식 | 모든 ID는 DB가 매기는 순번이다. 1차는 내 컴퓨터에서만 실행하고, 2차에는 소유자 검사로 보호한다. 로그인 없이 배포하게 되면 지원자 프로필 ID를 UUID로 바꾸는 것을 다시 검토한다. | 2026-11-26 |
| Q18 | Entity → DTO 변환 위치 | Service가 바꾼다. Service의 공개 메서드는 Entity를 돌려주지 않고 `dto` 패키지의 객체를 돌려준다. 변환은 트랜잭션 안에서 끝내고, 변환 코드는 DTO 쪽에 둔다(DTO가 Entity를 알고 Entity는 DTO를 모른다). Controller는 받은 DTO를 그대로 응답한다. 화면에 보내는 응답 객체와 다른 도메인에 주는 읽기 전용 객체는 이름으로 구분하고 함께 쓰지 않는다. | 2026-11-26 |
| Q19 | AI 호출의 대기와 실패 처리 | AI 호출(이력서 분석, 추천, 로드맵 생성)은 요청 안에서 끝날 때까지 기다린다. 화면은 진행 중 표시를 띄운다. 제한 시간(60초로 시작)을 넘기면 실패다. 실패하면 아무것도 저장하지 않고 화면에 실패 안내와 다시 시도 버튼을 보여 준다. 규칙만으로 만든 결과로 몰래 대신하지 않는다. AI의 답이 정해진 형식에 맞지 않을 때(후보에 없는 공고를 추천, 비중의 합이 맞지 않음 등)도 실패로 처리하며, 이 검사는 각 도메인의 OpenAI 구현체가 답을 도메인 객체로 바꿀 때 한다. | 2026-11-26 |
| Q20 | 저장소 폴더 구조 | 저장소 하나에 `backend/`(Spring Boot, Gradle, Java 17)와 `frontend/`(React, Vite, TypeScript)를 나란히 둔다. 루트에 `docker-compose.yml`(MySQL)을 둔다. 기본 패키지는 `com.gongchae.roadmap`이다. 개발할 때는 프론트엔드 개발 서버가 API 요청을 백엔드로 넘겨준다. Spring Boot와 React의 버전은 명세 단계에서 공식 문서로 확인해 정한다. | 2026-11-26 |
| Q21 | 샘플 데이터 | 잡알리오 연동 전까지 쓰는 mock 공고다. 키를 받은 뒤에도 테스트용으로 남긴다. 우리 도메인 구조(기관, 제목, 직무 분류, 접수 기간, 구조화된 전형 단계)의 JSON 파일로 직접 쓰고, `posting/infra`의 샘플 데이터 구현체가 읽는다. 날짜는 "실행한 날 + N일" 같은 상대 날짜로 적고 수집할 때 실제 날짜로 바꾼다. 30건으로 시작하며 진행 중과 마감, 전형 날짜가 모두 있음·일부 있음·없음, 필기 날짜가 겹치는 진행 중 공고 쌍을 섞는다. 기관 이름은 지어낸 것만 쓴다. 실제 잡알리오 응답 표본으로 변환을 검증하는 일은 실제 구현체를 만들 때 한다. | 2026-11-26 |
| Q22 | 직무 분류의 단위와 개수 | NCS 대분류 24개를 코드에 고정된 목록으로 쓴다. 공고는 직무 분류를 하나 이상, 지원자 프로필은 1개 이상 3개 이하로 가진다. 후보를 추릴 때 하나라도 겹치면 후보다. 잡알리오 코드(`R6000NN`, 표본상 `R600006` = 보건.의료 = 대분류 06)와 맞추는 일은 실제 구현체 안에서 코드정의서를 보고 한다. | 2026-11-26 |

## 조사로 확인한 사실

- 잡알리오 응답에 구조화된 전형 단계와 전형 일정은 없다. 항상 있는 날짜는 공고 시작일·종료일뿐이고(종료일 = 접수 마감일), 전형 절차는 자유 텍스트에만 있으며 그중 약 25%에만 날짜가 들어 있다. 첨부파일 다운로드 주소는 응답에 온다. 근거: `docs/research/job-data-sources.md` 5절 (2026-11-26)
- 버전(2026-11-26 공식 출처 확인). Java 17에서 쓸 수 있는 최신 안정 조합은 Spring Boot 4.2.x(현재 4.2.0, 무료 지원 2027-12-31까지) + Spring AI 2.1.x(현재 2.1.0)다. Spring Initializr가 Boot 4.2.0에 `org.springframework.ai:spring-ai-bom:2.1.0`을 짝짓고, OpenAI 스타터는 `org.springframework.ai:spring-ai-starter-model-openai`다. Gradle은 8.14 이상 또는 9.x, React 19, Vite 8(Node 20.19+ 또는 22.12+, 로컬 Node 24.12 사용 가능). 근거: `api.spring.io/projects/spring-boot/releases`, `api.spring.io/projects/spring-ai/releases`, `start.spring.io/dependencies?bootVersion=4.2.0`, `docs.spring.io/spring-boot/system-requirements.html`, `vite.dev/guide/`, `react.dev/versions`
- Spring AI 2.1: 모델의 답을 Java 레코드로 받는 기능은 ChatClient의 `.entity(레코드.class)`다. OpenAI는 최상위 배열을 받지 않으므로 목록은 레코드로 감싼다. 요청 제한 시간 설정은 `spring.ai.openai.timeout`(기본 60초)이다. 재시도 설정(`spring.ai.openai.max-retries` 기본 3, `spring.ai.retry.*`)이 따로 있어 Q19의 "제한 시간을 넘기면 실패"와 맞추려면 재시도 횟수를 함께 정해야 한다. 근거: `docs.spring.io/spring-ai/reference/api/chatclient.html`, `docs.spring.io/spring-ai/reference/api/chat/openai-chat.html`
- Spring AI 2.x는 OpenAI 모델에 공식 `openai-java` SDK를 쓰며 1.x와 설정 이름이 다르다. 1.x 기준의 글을 따르지 않는다. 2.1.0의 Getting Started 문서 본문에는 아직 2.0.x 기준 문장이 남아 있다
- Boot 4.2.0과 Spring AI 2.1.0은 나온 지 1주일이다. 초기 문제가 있으면 Boot 4.1.x + Spring AI 2.0.x(둘 다 무료 지원 2027-07-31까지)로 내린다. Spring AI 2.0.x를 Boot 4.2에 얹는 조합은 근거가 없어 쓰지 않는다

## 화면 디자인 반영 (2026-11-28)

화면 디자인을 별도 세션에서 Figma로 만들었다. 결과는 `docs/03-design.md`와 `docs/design/`의 그림이다. 디자인을 명세(#1)와 대조해 명세와 티켓 #5~#13을 고쳤다.

**API 응답에 더한 값.** 로드맵 응답에 로드맵을 만든 날, 공고 ID, 로드맵을 만든 날 기준의 진행 중 여부, 기한 지남 여부, 기간의 상태, 겹침 목록의 모양을 더했다. 추천 응답에 공고 ID를 더했다. 오류 응답의 코드가 오류의 종류를 구분하게 했다.

**받아들인 화면의 동작.** PDF와 글을 탭으로 나눠 하나만 보낸다. 형식·크기·길이를 화면이 먼저 검사한다. 로드맵이 있으면 추천 화면에서 넣은 공고를 미리 체크한다. 찾을 수 없음 화면, 날짜 미정 개수 안내, 날짜 반영 알림, 글자 수 표시, "접수 마감됨" 표시를 더했다. 준비 단계 안의 공고 줄 순서는 화면이 아니라 서버가 정한다.

**일정 규칙을 고친 것.** 디자인 세션이 화면의 상태를 그리다가 Q10과 Q11의 규칙에서 빈틈 다섯 개를 찾았다.

| # | 문제 | 고친 규칙 |
|---|---|---|
| 1 | 접수 마감일이 지나면 그 공고의 필기·면접 날짜가 로드맵에서 사라졌다. "마감 공고의 날짜는 쓰지 않는다"를 조회할 때마다 판단했기 때문이다 | 공고의 날짜를 쓰는지는 로드맵을 만든 날 기준으로 한 번 정한다. 만든 날에 진행 중 공고였으면 계속 쓴다 |
| 2 | 기한이 로드맵을 만든 날과 같으면 나눌 날이 없는데 "기한 지남"이라고 부르게 되어 있었다 | "기한 지남"과 "할 일에 기간이 없음"을 나눴다. 기간이 없는 이유는 날짜 미정, 남은 날 없음, 남은 날 부족 셋이다 |
| 3 | "기한 지남"의 기준이 로드맵을 만든 날이어서, 시간이 흘러 기한이 지나도 표시되지 않았다 | "기한 지남"은 오늘 기준으로 공고별 기한마다 판단한다. 할 일의 기간은 로드맵을 만든 날 기준으로 고정해 날이 지나도 바뀌지 않게 한다 |
| 4 | 남은 날이 할 일 수보다 적으면 겹치지 않게 나눌 수 없었다 | 할 일별로 나누지 않고 준비 단계 전체의 기간만 보여 준다 |
| 5 | 지난 기한 하나가 준비 단계 전체의 기간을 없앴다 | 할 일의 기간은 로드맵을 만든 날보다 뒤인 기한 중 가장 이른 것으로 계산한다. 지난 기한은 그 공고에만 "기한 지남"으로 표시한다 |

준비 단계의 순서는 다가오는 기한(오늘이거나 그 뒤인 기한 중 가장 이른 것) 순으로 바뀌었다.

**시안에 없는 모습.** 고친 규칙으로 생긴 모습(남은 날 없음과 남은 날 부족의 안내, 공고 줄의 "기한 지남" 표시)은 시안에 없고 `docs/03-design.md`의 글로만 정했다. 목록은 그 문서의 "시안에 없는 모습"에 있다.
